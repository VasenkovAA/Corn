# Corn (рабочее название)

![CI](https://github.com/VasenkovAA/Corn/actions/workflows/ci.yml/badge.svg)

Corn — это Open Source платформа для групповой связи и высококачественного стриминга, создаваемая как альтернатива Discord для небольших закрытых групп (друзей, команд разработки).

Проект делает акцент на производительности, контроле над данными и уникальных возможностях по управлению звуком.

## 🚀 Ключевые особенности

*   **Самостоятельное развертывание (Self-Hosted):** Вы можете запустить сервер на своем ПК или на выделенном сервере, полностью контролируя свои данные.
*   **Высококачественный стриминг:** Проект нацелен на обеспечение стабильного стриминга игр и рабочего стола в высоком разрешении (цель — 1080p@60FPS для MVP).
*   **Гибкое управление аудио:** Уникальная возможность для каждого участника звонка отдельно регулировать громкость голоса другого участника и звука его системы.
*   **Закрытые каналы:** Доступ к группам общения (каналам) осуществляется по временным, защищенным ссылкам-приглашениям.
*   **Кроссплатформенность:** Клиент разрабатывается для Windows и Linux.

## 🛠️ Технологический стек

*   **Язык:** [Rust](https://www.rust-lang.org/)
*   **Сервер:** [Axum](https://github.com/tokio-rs/axum) (веб-фреймворк) + [Tokio](https://tokio.rs/) (асинхронная среда)
*   **Клиент:** [Tauri](https://tauri.app/) (фреймворк для десктопных приложений)
*   **Медиа:** [WebRTC](https://webrtc.org/) для передачи аудио/видео в реальном времени
*   **База данных:** [PostgreSQL](https://www.postgresql.org/)
*   **Контейнеризация:** [Docker](https://www.docker.com/) & Docker Compose

## 👨‍💻 Для разработчиков

Этот раздел предназначен для тех, кто хочет внести свой вклад в проект.

### 1. Необходимое ПО

Перед началом работы убедитесь, что у вас установлены:
*   [Rust](https://www.rust-lang.org/tools/install) (стабильная версия)
*   [Docker](https://docs.docker.com/get-docker/) и [Docker Compose](https://docs.docker.com/compose/install/) или podman и podman-compose
*   [Python](https://www.python.org/downloads/) (для `pre-commit` или поставьте `pre-commit` как утилиту в linux)
*   [pre-commit](https://pre-commit.com/#installation) (`pip install pre-commit`)

### 2. Первоначальная настройка

1.  **Клонируйте репозиторий:**
    ```bash
    git clone git@github.com:VasenkovAA/Corn.git
    cd Corn
    ```

2.  **Установите Git-хуки:**
    Это **обязательный шаг**. Хуки будут автоматически проверять и форматировать ваш код перед каждым коммитом.
    ```bash
    pre-commit install
    ```

### 3. Запуск и разработка

*   **Запустить сервер для разработки:**
    ```bash
    cargo run -p cs-server
    ```

*   **Запустить тесты для всего проекта:**
    ```bash
    cargo test --all-targets
    ```

*   **Проверить код с помощью Clippy (линтер):**
    ```bash
    cargo clippy --all-targets -- -D warnings
    ```

*   **Отформатировать весь код:**
    ```bash
    cargo fmt --all
    ```

### 4. Структура проекта

Проект организован как **Cargo Workspace** (монорепозиторий), что позволяет легко управлять несколькими связанными компонентами. Все исходники находятся в папке `crates/`.

*   `crates/cs-server`: Крейт серверного приложения. Здесь вся логика бэкенда.
*   `crates/cs-client`: Крейт клиентского приложения на Tauri (в будущем).
*   `crates/cs-protocol`: Библиотечный крейт, содержащий общие структуры данных (например, сообщения для WebSocket), которые используются и клиентом, и сервером. **Никакой логики, только типы.**
*   `crates/cs-core`: Библиотечный крейт для общей логики, такой как кастомные ошибки, утилиты, общие константы (в будущем).
*   `crates/cs-webrtc`: Библиотечный крейт для общей логики работы с WebRTC (в будущем).

### 5. Процесс внесения изменений (Workflow)

1.  Создайте новую ветку от `development`: `git checkout -b feat/my-new-feature`.
2.  Внесите изменения в код.
3.  Запустите тесты и линтеры локально.
4.  Сделайте коммит. Pre-commit хуки выполнят автоматическую проверку.
    ```bash
    git add .
    git commit -m "feat: Реализована фича X"
    ```
5.  Отправьте изменения в репозиторий: `git push -u origin feat/my-new-feature`.
6.  Создайте Pull Request в ветку `development`. CI-пайплайн на GitHub выполнит все необходимые проверки.

Отлично, это очень важные уточнения. Согласованные правила по коммитам и веткам — залог чистоты истории Git и понятности процесса разработки.

Дополним наш `README.md`. Вот обновленный блок **"Для разработчиков"** с добавленными разделами. Можешь просто скопировать и заменить весь этот блок в своем файле.


#### 5.1. Ветки (Branches)

*   `main` — основная ветка. Она всегда должна быть в рабочем состоянии и готова к релизу. Прямые коммиты в `main` запрещены.
*   **Feature-ветки** — для разработки нового функционала. Название ветки должно отражать ее суть.

**Правила именования веток:**

Используйте префиксы для классификации изменений:
*   `feat/` — для новой функциональности (например, `feat/add-user-registration`).
*   `fix/` — для исправления ошибок (например, `fix/login-button-not-working`).
*   `refactor/` — для рефакторинга кода без изменения функциональности (например, `refactor/move-db-logic-to-repository`).
*   `docs/` — для изменений в документации (например, `docs/update-readme`).
*   `chore/` — для прочих изменений, не затрагивающих исходный код (например, `chore/update-ci-config`).

**Пример создания ветки:**
```bash
git checkout -b feat/add-channel-creation
```

#### 5.2. Коммиты (Commits)

Мы придерживаемся стандарта [Conventional Commits](https://www.conventionalcommits.org/). Это помогает автоматизировать генерацию списка изменений (changelog) и делает историю Git читаемой.

**Формат коммита:**
```
<тип>(<область>): <краткое описание>

[опциональное тело коммита с подробностями]

[опциональный футер]
```
*   **Типы коммитов:**
    *   `feat`: Новая функция.
    *   `fix`: Исправление бага.
    *   `refactor`: Рефакторинг кода.
    *   `docs`: Изменения в документации.
    *   `style`: Изменения форматирования, не влияющие на код.
    *   `test`: Добавление или исправление тестов.
    *   `chore`: Обслуживание репозитория (обновление CI, зависимостей и т.д.).
*   **Область (scope):** Опциональное поле, указывающее на часть проекта, которую затронул коммит. Например: `cs-server`, `cs-protocol`, `ci`.
**Примеры хороших сообщений коммитов:**
```
feat(cs-server): Add WebSocket endpoint for joining a channel
```
```
fix(cs-protocol): Correct serialization of HelloMessage
```
```
docs: Update README with branching strategy
```
```
refactor(cs-server): Move database connection logic to db module
```
#### 5.3. Pull Request'ы (PR)
1.  Создайте ветку от `development`, как описано выше.
2.  Внесите изменения в код, следуя правилам оформления коммитов.
3.  Отправьте изменения в удаленный репозиторий: `git push -u origin feat/my-new-feature`.
4.  Создайте Pull Request (PR) из вашей ветки в `main`.
5.  **Оформление PR:**
    *   **Заголовок:** Должен быть кратким и информативным, часто можно использовать заголовок основного коммита.
    *   **Описание:** Кратко опишите, **что** и **зачем** было сделано.
6.  Дождитесь прохождения всех проверок в CI.
7.  После одобрения и успешного прохождения CI, PR будет влит в `development`.
