### 1. Архитектура репозитория: Monorepo с Cargo Workspace

Для проекта, состоящего из тесно связанных компонентов (клиент, сервер, общие протоколы), нет ничего лучше, чем **монорепозиторий на базе Cargo Workspaces**.

**Почему?**
*   **Атомарные изменения:** Вы меняете протокол обмена данными — вы меняете его в одном коммите и для клиента, и для сервера. Никакого ада с версиями зависимостей между репозиториями.
*   **Общий код:** Легко выносить общую логику (протоколы, типы ошибок, утилиты) в отдельные крейты (crates) внутри воркспейса.
*   **Единый CI/CD:** Один набор проверок и один пайплайн для сборки и деплоя всего проекта.

### 2. Структура каталогов и файлов

Вот иерархия, которую я бы создал в корне репозитория:

```
Corn/
├── .github/
│   └── workflows/
│       ├── ci.yml          # Основной CI-пайплайн
│       └── release.yml     # Пайплайн для создания релизов
├── .vscode/                # Настройки для VS Code (rust-analyzer)
│   └── settings.json
├── crates/                 # Директория с исходным кодом всех наших крейтов
│   ├── cs-client/          # Крейт клиентского приложения (Tauri)
│   │   ├── src/
│   │   ├── tauri.conf.json
│   │   └── Cargo.toml
│   ├── cs-server/          # Крейт серверного приложения
│   │   ├── src/
│   │   └── Cargo.toml
│   ├── cs-protocol/        # Крейт с общими структурами данных
│   │   ├── src/
│   │   └── Cargo.toml
│   ├── cs-webrtc/          # Крейт для общей логики WebRTC
│   │   ├── src/
│   │   └── Cargo.toml
│   └── cs-core/            # Крейт с базовой логикой (ошибки, конфиги, логгирование)
│       ├── src/
│       └── Cargo.toml
├── docker/
│   ├── docker-compose.yml  # Docker Compose для локального запуска
│   └── server/
│       └── Dockerfile      # Dockerfile для сборки серверного приложения
├── .gitignore
├── .pre-commit-config.yaml # Конфигурация для pre-commit хуков
├── Cargo.toml              # Главный Cargo.toml, определяющий workspace
└── README.md
```

**`Cargo.toml` в корне:**
```toml
[workspace]
members = [
    "crates/cs-client",
    "crates/cs-server",
    "crates/cs-protocol",
    "crates/cs-webrtc",
    "crates/cs-core",
]
resolver = "2" # Используем новый, более умный resolver зависимостей

[workspace.dependencies]
# Здесь мы определяем общие зависимости и их версии
tokio = { version = "1", features = ["full"] }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
tracing = "0.1"
# ... и так далее
```
Это позволяет всем крейтам использовать одну и ту же версию `tokio`, `serde` и т.д., просто указав в своем `Cargo.toml` `tokio = { workspace = true }`.

### 3. CI и Pre-commit: ловим ошибки как можно раньше

**Философия:** Быстрые проверки — локально (pre-commit). Долгие и полные — в CI.

#### 3.1. Pre-commit Hooks (`.pre-commit-config.yaml`)

Эти хуки запускаются автоматически перед каждым коммитом, экономя время и ресурсы CI.
```yaml
repos:
-   repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.4.0
    hooks:
    -   id: check-yaml
    -   id: end-of-file-fixer
    -   id: trailing-whitespace
-   repo: https://github.com/doublify/pre-commit-rust
    rev: v1.0
    hooks:
    -   id: fmt              # cargo fmt -- --check
    -   id: clippy           # cargo clippy -- -D warnings (строго, но правильно)
    -   id: cargo-check      # Быстрая проверка на ошибки компиляции
```

#### 3.2. CI-пайплайн (`.github/workflows/ci.yml`)

Этот пайплайн запускается на каждый Push и Pull Request.
```yaml
name: CI

on: [push, pull_request]

jobs:
  test_and_lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: dtolnay/rust-toolchain@stable
        with:
          components: rustfmt, clippy

      - name: Run Formatter Check
        run: cargo fmt --all -- --check

      - name: Run Clippy
        run: cargo clippy --all-targets -- -D warnings

      - name: Run Tests
        run: cargo test --all-targets

      - name: Build All Crates (Release)
        run: cargo build --all-targets --release

  security_audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: taiki-e/install-action@cargo-deny
      - name: Check for security vulnerabilities
        run: cargo deny check advisories

  license_check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: taiki-e/install-action@cargo-deny
      - name: Check dependency licenses for MIT compatibility
        # Проверяем, что все зависимости имеют совместимые лицензии (MIT, Apache-2.0, BSD)
        run: cargo deny check licenses
```
**Ключевые проверки в CI:**
1.  **Форматирование и Линтинг (`fmt`, `clippy`):** Гарантируют единый стиль кода.
2.  **Тесты (`test`):** Прогоняют все unit и integration тесты.
3.  **Сборка (`build`):** Убеждаемся, что проект собирается в release-режиме без ошибок.
4.  **Аудит безопасности (`cargo-deny check advisories`):** Критически важно. Проверяет все зависимости на известные уязвимости (CVE).
5.  **Проверка лицензий (`cargo-deny check licenses`):** Для Open Source проекта с лицензией MIT это **обязательно**. Гарантирует, что вы случайно не втянули зависимость с несовместимой лицензией (например, GPL).

### 4. Предлагаемые технологии и структура модулей

Теперь погрузимся в код.

**Общие технологии:**
*   **Асинхронщина:** `tokio` — без вариантов, это стандарт.
*   **Логгирование:** `tracing` — современная, структурированная, async-aware система. Гораздо мощнее, чем `log`.
*   **Обработка ошибок:** `thiserror` для создания кастомных типов ошибок в библиотечных крейтах (`cs-core`, `cs-protocol`) и `anyhow` для простой обработки ошибок в бинарных крейтах (`cs-server`, `cs-client`).
*   **Сериализация:** `serde` — стандарт для JSON и других форматов.

#### 4.1. Крейт `cs-protocol`
Самый простой, но самый важный крейт. Содержит только структуры данных.
```rust
// crates/cs-protocol/src/lib.rs
use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize, Debug)]
pub enum ClientMessage {
    JoinChannel { channel_id: String, token: String },
    SendChatMessage { content: String },
    WebRtcOffer { sdp: String },
    // ...
}

#[derive(Serialize, Deserialize, Debug)]
pub enum ServerMessage {
    Welcome { user_list: Vec<String> },
    NewChatMessage { author: String, content: String },
    WebRtcAnswer { sdp: String },
    // ...
}
```

#### 4.2. Крейт `cs-server`
Здесь будет вся основная логика сервера.

**Предлагаемый стек:**
*   **Веб-сервер и WebSocket:** `axum`. Это современный, модульный фреймворк поверх `tokio` и `hyper`, идеально подходящий для этой задачи.
*   **База данных:** `sqlx` с `sqlx::query_as!`. **Ключевое преимущество — проверка SQL-запросов на этапе компиляции**. Это устраняет огромный класс ошибок.
*   **WebRTC:** `webrtc.rs` (библиотека, которую мы обернем в `cs-webrtc`).

**Структура модулей в `cs-server/src/`:**
```
src/
├── main.rs         // Точка входа: парсинг конфига, запуск сервера
├── config.rs       // Логика загрузки конфигурации
├── error.rs        // Тип ошибки верхнего уровня для сервера
├── state.rs        // Глобальное состояние сервера (списки каналов, юзеров), защищенное мьютексами
├── db.rs           // Настройка пула соединений с БД (sqlx)
└── network/
    ├── mod.rs
    ├── ws.rs         // Логика WebSocket: обработка подключений, роутинг сообщений
    └── webrtc.rs     // Логика сигнализации для WebRTC (обмен Offer/Answer)
└── channel/
    ├── mod.rs
    └── manager.rs    // Логика управления каналами: создание, удаление, управление участниками
```

**По поводу мультиплексирования потоков в одном WebSocket:** Это стандартный подход. Вы отправляете JSON-сообщения (`ClientMessage`/`ServerMessage`), а WebRTC уже сам устанавливает отдельное peer-to-peer соединение (зашифрованное по DTLS-SRTP) для передачи медиа. WebSocket нужен только для "договоренности" (сигнализации).

#### 4.3. Крейт `cs-client` (Tauri)
**Почему Tauri?**
1.  **Написан на Rust:** Бэкенд вашего десктопного приложения — это Rust. Идеальная интеграция.
2.  **Малый размер:** Использует системный webview, поэтому итоговый бинарник гораздо меньше, чем у Electron.
3.  **Безопасность:** Четко определенный мост между JS-фронтендом и Rust-бэкендом.

**Структура `cs-client`:**
*   `src/`: Rust-часть приложения. Здесь будет логика подключения к серверу, управление WebRTC-сессией, обработка медиапотоков (захват экрана/аудио), взаимодействие с ОС.
*   `src-tauri/`: Конфигурация Tauri.
*   **Фронтенд-часть (внутри `src/` или в отдельной папке):** На любом JS-фреймворке (Svelte, Vue, React). Здесь рисуется UI, который общается с Rust-бэкендом через команды Tauri.

**Захват медиа:**
*   **Linux:** Вы правы, `pipewire` через `xdg-desktop-portal` — правильный путь. Для этого есть крейты, например `ashpd`.
*   **Windows:** Вам нужно будет использовать `windows-rs` крейт для вызова нативных API: **Windows Graphics Capture API** для экрана и **WASAPI Loopback** для системного звука. Это не самая тривиальная задача, но вполне решаемая. Обертывание этого в кроссплатформенный API внутри `cs-client` будет одной из ключевых задач.
