### План разработки на первую неделю (14 часов)

**Цель недели:** Создать минимально работающий сервер, который может принимать WebSocket-соединения, обрабатывать простое сообщение и хранить данные в PostgreSQL.

---

#### **День 1 (2 часа): Настройка окружения и первый "Hello, World" сервер**

*   **Задача:** Убедиться, что все инструменты работают, и запустить самый базовый веб-сервер.
*   **Шаги:**
    1.  **Настройка Docker (45 мин):**
        *   Создать в проекте папку `docker/`.
        *   Внутри нее создать файл `docker-compose.yml`.
        *   Прописать в нем сервис для `postgres` с указанием пароля, пользователя и именованного тома (volume) для сохранения данных.
        *   Запустить `docker-compose up -d` и убедиться, что контейнер с PostgreSQL успешно стартовал (`docker ps`).
    2.  **Интеграция `axum` (60 мин):**
        *   Добавить `axum` в `[workspace.dependencies]` в корневом `Cargo.toml`.
        *   Добавить `axum` и `tokio` в зависимости крейта `cs-server`.
        *   В `cs-server/src/main.rs` написать простейший `axum` сервер, который на запрос `GET /` отвечает текстом "Hello, Corn!".
    3.  **Проверка (15 мин):**
        *   Запустить сервер: `cargo run -p cs-server`.
        *   Открыть в браузере `http://127.0.0.1:3000` (или какой порт вы выберете) и увидеть приветствие.

---

#### **День 2 (2 часа): Подключение к базе данных**

*   **Задача:** Научить наш сервер "общаться" с базой данных PostgreSQL.
*   **Шаги:**
    1.  **Интеграция `sqlx` (30 мин):**
        *   Добавить `sqlx` (с фичами `runtime-tokio-rustls`, `postgres`) в `[workspace.dependencies]`.
        *   Добавить `dotenvy` для удобной работы с переменными окружения.
    2.  **Создание модуля для БД (75 мин):**
        *   В `cs-server/src` создать файл `db.rs`.
        *   В нем написать функцию `create_pool()`, которая читает строку подключения к БД из переменных окружения (например, `DATABASE_URL`) и создает пул соединений `PgPool`.
        *   В `main.rs` вызвать эту функцию и проверить, что соединение устанавливается без ошибок при старте сервера. Для этого можно выполнить простой запрос `SELECT 1`.
    3.  **Переменные окружения (15 мин):**
        *   Создать в корне проекта файл `.env` (и добавить его в `.gitignore`!).
        *   Прописать в нем `DATABASE_URL="postgres://user:password@localhost:5432/dbname"`.

---

#### **День 3 (2 часа): WebSocket-эндпоинт**

*   **Задача:** Добавить на сервер возможность принимать не только HTTP-запросы, но и WebSocket-соединения.
*   **Шаги:**
    1.  **Создание эндпоинта (60 мин):**
        *   В `main.rs` добавить новый роут, например, `/ws`.
        *   Написать обработчик (handler), который "апгрейдит" HTTP-соединение до WebSocket.
    2.  **Обработка сообщений (60 мин):**
        *   В обработчике создать цикл, который будет слушать входящие сообщения от клиента.
        *   При получении любого сообщения, просто выводить его в консоль (`println!`) и отправлять обратно клиенту сообщение "Pong".

**Как проверить:** Использовать любой простой WebSocket-клиент, например, расширение для браузера или онлайн-инструмент.

---

#### **День 4 (2 часа): Структурирование проекта и обработка ошибок**

*   **Задача:** Навести порядок в коде, чтобы он был готов к усложнению.
*   **Шаги:**
    1.  **Интеграция `thiserror` и `anyhow` (30 мин):**
        *   Добавить крейты в `[workspace.dependencies]`.
    2.  **Создание кастомных ошибок (45 мин):**
        *   В `cs-server` создать файл `error.rs`.
        *   Определить главный тип ошибки для сервера `AppError` и реализовать для него `IntoResponse`, чтобы `axum` мог красиво преобразовывать ошибки в HTTP-ответы.
    3.  **Рефакторинг (45 мин):**
        *   Вынести логику WebSocket в отдельный модуль, например, `cs-server/src/network/ws.rs`.
        *   Заменить все `.unwrap()` и `.expect()` в коде на обработку ошибок через оператор `?` и новый тип `AppError`.

---

#### **День 5 (2 часа): Протокол и состояние сервера**

*   **Задача:** Заставить сервер и клиент общаться на "одном языке" и хранить состояние подключенных клиентов.
*   **Шаги:**
    1.  **Расширение протокола (30 мин):**
        *   В `cs-protocol` определить два `enum`-а: `ClientMessage` и `ServerMessage` с помощью `serde`.
        *   Начать с простого: `ClientMessage::Ping` и `ServerMessage::Pong`.
    2.  **Обработка протокола (60 мин):**
        *   В обработчике WebSocket (`ws.rs`) теперь не просто читать текст, а десериализовать JSON в `ClientMessage`.
        *   Использовать `match` для обработки разных типов сообщений. На `Ping` отвечать сериализованным `Pong`.
    3.  **Глобальное состояние (30 мин):**
        *   В `cs-server` создать файл `state.rs`.
        *   Определить структуру `AppState`, которая будет хранить, например, `HashMap` с подключенными клиентами. Обернуть ее в `Arc<Mutex<...>>` для потокобезопасного доступа.
        *   Передать это состояние в обработчики `axum` с помощью `.with_state()`.

---

#### **Дни 6-7 (4 часа): Регистрация пользователей и первая миграция БД**

*   **Задача:** Реализовать первую осмысленную бизнес-логику: пользователь подключается, мы его регистрируем и сохраняем в БД.
*   **Шаги:**
    1.  **Интеграция `sqlx-cli` (День 6, 30 мин):**
        *   Установить `cargo install sqlx-cli`.
        *   Создать папку `migrations` в `cs-server` с помощью `sqlx migrate add create_users_table`.
    2.  **Создание миграции (День 6, 45 мин):**
        *   В сгенерированном SQL-файле написать запрос на создание таблицы `users` (например, с полями `id`, `username`, `created_at`).
        *   Применить миграцию: `sqlx migrate run`.
    3.  **Обработка "регистрации" (День 6, 45 мин):**
        *   Добавить в `cs-protocol` новый вариант `ClientMessage::Register { username: String }`.
        *   В обработчике WebSocket при получении этого сообщения, добавлять нового пользователя в таблицу `users` в БД.
    4.  **Рефакторинг и тесты (День 7, 2 часа):**
        *   Вынести логику работы с пользователями из обработчика `ws.rs` в отдельный модуль, например `cs-server/src/user.rs`.
        *   Написать **первый интеграционный тест**, который эмулирует подключение к БД (можно использовать тестовую БД), добавляет пользователя и проверяет, что он действительно появился в таблице. Это очень важный шаг для обеспечения качества.
