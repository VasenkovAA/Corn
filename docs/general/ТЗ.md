### **Техническое Задание (ТЗ)**
**Название проекта:** Платформа для групповой связи и стриминга (условное название "Corn")
**Версия документа:** 1.0
**Дата:** 07.11.2025

### 1. Общие положения

#### 1.1. Назначение документа
Настоящее Техническое Задание определяет требования к разработке программного обеспечения для организации конференц-связи с фокусом на высококачественный стриминг игр и демонстрацию экрана для небольших закрытых групп.

#### 1.2. Определения и терминология
*   **Серверное приложение (СП):** Docker-композиция, состоящая из основного бэкенд-приложения и базы данных. Разворачивается либо локально на ПК пользователя, либо на выделенном сервере.
*   **Канал:** Изолированное пространство для общения внутри СП, аналог "сервера" в Discord. Имеет свой список участников, администратора и постоянный текстовый чат.
*   **Администратор Канала:** Пользователь, создавший Канал. Имеет полные права на управление Каналом, включая генерацию ключей доступа.
*   **Пользователь:** Любой участник, подключенный к СП.
*   **Ключ доступа:** Временный, генерируемый токен (в виде ссылки), содержащий всю информацию для подключения к конкретному Каналу.

### 2. Назначение и цели проекта

Создание клиент-серверного приложения, являющегося альтернативой Discord для узкого круга лиц (друзья, команды разработки), со следующими ключевыми целями:

*   **Обеспечение высококачественного стриминга** игр и рабочего стола.
*   **Предоставление уникальной возможности раздельного управления аудиопотоками** (голос, звук системы) на стороне клиента для максимального комфорта пользователей.
*   **Создание закрытой и контролируемой среды** для общения через систему Каналов и ключей доступа.
*   **Проект является Open Source**.

### 3. Требования к продукту

#### 3.1. Функциональные требования

**3.1.1. Архитектура и модель развертывания**
1.  Серверное приложение должно поставляться в виде набора Docker-контейнеров, управляемых через `docker-compose.yml`.
2.  Набор должен включать как минимум два контейнера: основной бэкенд и базу данных PostgreSQL.
3.  Данные PostgreSQL должны храниться в именованном Docker-томе (volume) для обеспечения сохранности при перезапуске/обновлении контейнера с бэкендом.
4.  Поддерживаются два сценария развертывания:
    *   **Локальный:** СП запускается на том же ПК, что и клиент.
    *   **Удаленный:** СП запускается на выделенном сервере, доступ к которому осуществляется по IP-адресу или DNS-имени (включая Dynamic DNS).

**3.1.2. Управление Каналами и Пользователями**
1.  Любой пользователь, подключенный к СП, может создать свой собственный Канал и автоматически становится его Администратором.
2.  Клиентское приложение должно иметь боковую панель для отображения списка Каналов, к которым у пользователя есть доступ, и для переключения между ними.
3.  Идентификация пользователя двухуровневая:
    *   При первом подключении к СП пользователь задает себе "глобальное" имя.
    *   При входе в каждый конкретный Канал пользователь задает себе локальное имя (никнейм) для этого Канала.

**3.1.3. Система доступа и шифрования**
1.  Доступ к Каналу осуществляется исключительно по Ключу доступа, генерируемому Администратором Канала.
2.  При генерации Ключа Администратор должен иметь возможность задать:
    *   Срок действия ключа (время жизни).
    *   Максимальное количество использований (число подключений).
3.  Каждый Канал должен использовать свой уникальный ключ для шифрования медиатрафика. Этот ключ должен быть частью Ключа доступа к каналу.
4.  Весь медиатрафик (аудио, видео) должен быть зашифрован (например, с использованием DTLS-SRTP, стандартного для WebRTC).

**3.1.4. Функционал звонков и стриминга**
1.  Поддержка групповых звонков с участием до 15 человек.
2.  **Демонстрация экрана:**
    *   Пользователь, начинающий стрим, должен иметь возможность выбрать качество трансляции (разрешение и FPS).
    *   **Ключевое требование:** Приложение должно захватывать и передавать аудио- и видеопотоки как отдельные треки. Как минимум:
        *   Голос пользователя (с микрофона).
        *   Звук операционной системы (с игры, плеера и т.д.) - в будующем хотели бы захватывать звук не всего рабочего стола, а конкретного приложения, но пока это не планируем.
        *   Видео (демонстрируемый экран).
    *   Архитектура должна быть готова к добавлению дополнительных потоков (например, видео с веб-камеры, второй микрофон).
3.  **Управление звуком на клиенте:**
    *   Каждый принимающий пользователь должен видеть в интерфейсе отдельные регуляторы громкости для каждого входящего аудиопотока от каждого участника (например: `Громкость [User1_Mic]`, `Громкость [User1_System_Audio]`).
4.  **Шумоподавление:** Должна быть реализована функция шумоподавления для микрофонного аудиопотока с использованием готовых Open Source библиотек (например, SpeexDSP), совместимых с лицензией MIT.

**3.1.5. Текстовый чат**
1.  В каждом Канале должен быть реализован постоянный (persistent) текстовый чат.
2.  История чата хранится на сервере в базе данных PostgreSQL(текст сообщений зашифрован) и подгружается клиентом при подключении к Каналу.

#### 3.2. Нефункциональные требования

1.  **Производительность:**
    *   **Цель для MVP:** Стабильный стриминг в разрешении **1080p при 60 FPS**.
    *   **Цель для будущих версий:** Поддержка **4K при 60 FPS**.
    *   Задержка передачи сигнала (latency) до 0.5 секунды является приемлемой.
2.  **Совместимость (Клиент):**
    *   **Первый приоритет:** Windows, Linux.
    *   **Второй приоритет (не в MVP):** macOS.
3.  **Лицензирование:** Все используемые сторонние библиотеки и фреймворки должны иметь пермиссивные лицензии (MIT, Apache 2.0, BSD и т.п.), совместимые с основной лицензией проекта (MIT).

### 4. Рекомендуемый технологический стек

**4.1. Протоколы и медиа**
*   **Транспорт медиа:** **WebRTC**. Этот фреймворк является отраслевым стандартом, имеет открытый исходный код, решает задачи NAT-траверсала, адаптации к качеству сети и позволяет передавать несколько медиа-треков в рамках одного соединения.
*   **Сигнализация (Signaling):** **WebSocket**. Будет использоваться для установки WebRTC-соединения, обмена метаданными и для работы текстового чата.
*   **Видеокодек (MVP):** **H.264**. Самый распространенный и аппаратно-ускоряемый на большинстве устройств кодек.
*   **Аудиокодек:** **Opus**. Стандарт для WebRTC, обеспечивает высокое качество речи и звука при низкой задержке.

**4.2. Клиентское приложение**
*   **Технология захвата экрана/аудио:**
    *   **Linux:** **PipeWire** (через xdg-desktop-portal).
    *   **Windows:** **Windows Graphics Capture API** для видео и **WASAPI (Audio Loopback)** для системного аудио.
*   **Фреймворк для UI:** **Tauri** или **Electron**. Tauri предпочтительнее из-за меньшего потребления ресурсов, но Electron имеет более низкий порог входа. Выбор остается за командой разработки.

**4.3. Серверное приложение**
*   **Язык программирования:**  **Rust**.
*   **База данных:** **PostgreSQL**.

### 5. Требования к UI/UX

*   Для MVP создается минималистичный, функциональный интерфейс без сложных графических элементов.
*   Основная структура интерфейса должна повторять логику Discord: боковая панель со списком Каналов, основная область для чата/видео.
